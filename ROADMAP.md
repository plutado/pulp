# Roadmap

Estimates are working hours for one developer, including tests and docs. They are rough; the total range reflects that. Checked items are done. The "still open" row is the sum of the unticked items' own estimates, not the previous figure minus what was finished — recompute it from the items, or it drifts.

## Where things stand

**Milestone 28, per-layer timing, transitions and looks, is done:** a layer has its own start, end, entrance, exit and look, with a bar per layer under the scrub bar. Milestone 30 is done before it — 85 of the 124 bundled templates declare how they stretch, and the other 39 move all the way through and keep their fixed length — and milestones 26 and 29 before that. Everything before it on the planned order is finished: the renderer and alpha export, the parameter editor, the library with search and categorization, drag-out, packs, the window shell and visual polish, browse and preview, collections, vertical and square formats, the sample library, image slots, layers, the browse panel's find field, and layers moved and resized on the stage. 124 bundled CC0 templates, a 481-file sample-media catalogue, 66 types / 51 themes / 11 styles in the taxonomy, every category at least six deep and every theme with at least three assets of its own.

What is left: social-ready export (20), 1.0 hardening and docs (8), then packaging — unsigned builds (17) and signing (7). Milestones 27 (projects and the application menu, next in the suggested order), 31, 32 and 33 are decided but not yet scheduled. Four verification items wait on hardware: two need the test Mac, two a Windows machine (see `docs/ideas.md`, Decided item 1, which replaces "hardware-blocked" with a Windows VM). Known issues and anything not yet scheduled are in `docs/ideas.md`.

Milestones keep the number they were given when they were added. Milestones 1 to 23 have GitHub issues of the same number; from 24 on, a new milestone's issue number is given beside its heading, since pull requests share GitHub's numbering. Ideas, decisions not yet scheduled and known issues wait in `docs/ideas.md` until a milestone takes them. The table and the sections below are in **planned order**, which is not numeric order. Packaging and signing (17 and 7) come last, after hardening: packaging is the final step, and what it wraps should be the finished thing. The window layout that the UI milestones build, and why they come in this order, is in `docs/ui-layout.md`.

## 1. Headless frame renderer, production quality (12-20 h)

A first renderer works (offscreen window, PNG frames to ffmpeg). This milestone makes it dependable.

- [x] Automated end-to-end render test that runs when Electron and ffmpeg are available, checking frame count, size and alpha with ffprobe (2-3 h)
- [x] HiDPI: render at device scale 1 explicitly instead of resizing captured frames; verified on a Retina display (2-3 h)
- [x] HiDPI: verify on Windows at 150% scaling. Verified by simulated 150% scaling on Windows CI: the e2e suite renders with Chromium's `--force-device-scale-factor=1.5` (the primary display reports 1.5, as Windows does at 150%) and checks the frames stay pixel-exact; the `windows-latest` job runs the whole suite with `PULP_E2E=1` and passed on ffmpeg 9.0.2 (1 h)
- [x] Large frames: verify 4K and 8K, and portrait sizes for vertical video (1-2 h)
- [x] Throughput: avoid PNG encode/decode by piping raw BGRA (`-f rawvideo -pixel_format bgra`) from `capturePage()`, with `unpremultiply` for alpha templates (ADR 0003 explains why not the `paint` event); benchmarked against the PNG path in `docs/system-design.md` (3-5 h)
- [x] Color: decide and document sRGB/Rec.709 handling: video presets convert with the BT.709 matrix to limited range and tag every frame BT.709 (`scale` + `setparams`), PNG stays sRGB; ADR 0004 (2-3 h)
- [x] Robustness: per-frame timeout for hung templates, delete partial output on cancel or failure, clear errors when a template throws (1-2 h)
- [x] Render queue: several renders in sequence with progress per job (1-2 h)

- [x] Media files: type inferred from the media kind plus folder names (`sfx/whoosh/…` → whoosh; type ids, labels and plurals all match; no folder means no type rather than a guess), built-in themes collected along the path (`Sports/Hockey/…`); user themes — built-in or custom — editable in the Info tab next to the tags, stored in `user_items` like tags (schema migration keeps existing user data) and surviving offline roots; the Info details line names the type (2-3 h)
- [x] Search: `type:` takes a taxonomy type or a type group as well as the media kinds (several `type:` terms are alternatives), `theme:` matches manifest, folder and custom themes (all terms required), `style:` matches a template's declared styles; all combine with the existing filters, free text finds types and themes by id, and the filters are listed in the search field's hint. - [x] Browse tree in the browse panel (`src/core/browse-tree.ts`, pure and tested), replacing milestone 11's flat node list: Quick access (Favorites, Recently used), Types (group → type, with an Untyped node for templates of category "other" and media no folder typed), Themes (built-in groups plus a Custom group), Styles and Folders ("Built-in templates" first), each node with a count. Packs join the tree when pack defaults land (3-5 h)
- [x] Packs: `pack.json` may declare a default `type`, `themes` and `styles` for its templates (validated like a manifest; a template's own type wins, themes and styles join); any folder with a `pack.json` counts as a pack during the scan, its templates remember it, `pack:<slug>` searches it, and the tree has a Packs section with counts; spec and tests updated (1 h)

## 13. Collections (10-17 h)

Turns the queue in the collection tray into collections; the separate queue panel goes away. The drag-out experience is rebuilt here first, because collections inherit its cards.

- [x] Render cards, replacing the drag-out corner that predated the layout and style work: each job is a card with a thumbnail, the item's display name, the preset as a badge and one line of status (queued, a progress bar, done, or the reason it failed). A finished card **is** the drag source — a grip, the whole card draggable, a "Drag to your editor" hint on hover and focus — so there is one drag affordance instead of a card plus a separate handle. No path or file name in a card's text: the path is in the tooltip and behind Reveal in Finder / Show in Explorer, Copy path and Remove, which also give a keyboard a way to the file since dragging needs a pointer. "Prepare for drag" became an action on the item next to Render, and lands a card whether it rendered or reused the cache. The standing cache-link paragraph became an info icon with a tooltip plus a one-time notice the first time something is dragged out. Card text comes from a pure `src/core/queue-card.ts` with unit tests, and the style test now forbids first-person wording and raw paths in visible text (2-3 h)
- [x] Collection tray: items added from the stage's Add to collection or by dragging a results card onto the tray, as cards in the same shape as the render cards — thumbnail, name, duration badge, and a line saying what the item's own settings are. Choosing a card hands it to the inspector's Output and Parameters tabs, so an item is edited with the same controls as anything else rather than a second copy of them inside the card; every change writes back. Remove, reorder with the arrows, and Apply to all, which gives every item the chosen card's output settings and leaves their parameters alone. The collection itself is a pure `src/core/collection.ts` with unit tests (2-4 h)
- [x] Save and load a collection as a `.pulpcollection` file, written atomically like the rest. Items are recorded twice over: by library id, which is a hash of where the file sits and survives a rescan, and — for a template — by its manifest id, which travels between libraries; loading tries the first and falls back to the second. What the library cannot answer for is flagged on its card and counted on load rather than dropped, so a collection is also a record of what a project used. A file in an unknown format is refused with its version named, and an item that cannot be read is skipped without losing the rest (2-3 h)
- [x] Render all: one folder chosen once, then a job per item carrying that item's own preset, options and parameters, through the same queue as everything else. Per-item progress on each card, total progress in the tray head; two items of the same name do not render over each other. Items the library cannot reach, and media (converting it is milestone 15), are named as skipped rather than silently dropped, and the rest still renders. Finished items become the draggable render cards from this milestone's first item. The folder dialog cannot be driven over the DevTools protocol, so the render path is proved headlessly with `--collection` (3-5 h)
- [x] Headless: `--collection <file>` renders a saved collection into `--out`, each item with its own settings, naming and skipping what the library cannot answer for. The end-to-end test renders one collection with two settings of the same template plus a missing template and a media item, and checks both outputs and both skips (1-2 h)

## 19. Vertical and square formats (13-21 h)

Before milestone 8, which writes the authoring guide and the JSON Schema: both should describe the format as it ends up, not one that is about to change underneath them.

**A template is defined by its aspect ratio, not by a pixel size.** A lower third is a lower third at 1920 × 1080 and at 1080 × 1920; what differs is the shape of the canvas and where things sit in it. Today's manifest declares `width` and `height`, which pins every template to one resolution and makes a vertical version a second template to write and maintain. This milestone moves the pixel size to render time and leaves the template saying only which shapes it is drawn for.

- [x] Template format: a template declares the aspect ratios it supports (`aspects`: 16:9, 9:16, 1:1, 4:5) instead of a pixel size, and draws relative to the canvas it is handed; the frame state's `width` and `height` are now the render's, passed in by the caller rather than read off the manifest. The output resolution is chosen at render time through a pure `src/core/aspect.ts` (standard sizes per aspect, 720p to 4K and 8K for 16:9; an exact size; the checks that a size is of its aspect), carried in the render options as `aspect`, `width` and `height` and as the headless `--aspect` and `--size` flags. Manifests with `width` and `height` keep working: the aspect is inferred (a built-in one within 1%, else the reduced ratio such as 4:3, at which the template renders at that one size) and the size becomes the default resolution. The renderer sizes its offscreen window from the plan's size rather than the manifest, the capture-size check and ffmpeg's input follow it, and thumbnails, hover-scrub strips and the preview take the template's default size. The library re-reads templates once (schema 5) so stored manifests carry their aspects. Validator with tests, `docs/template-format.md`, ADR 0012; the render test proves a shape-only fixture at its default, tall with `--aspect`, square with `--size`, and the refusals (4-6 h)
- [x] Output tab: an aspect choice for templates that support more than one (hidden otherwise), and a resolution for every template — the template's own size or the aspect's default first, the standard list for that aspect, then a custom width and height checked against the aspect — carried in the render options, written to the collection card being edited, and read back from one. The preview follows the choice through a shared `frameSize` signal: the box takes the shape and the template is drawn for that canvas. The options note names the size when it is not the template's own, and a size that is not of the aspect blocks Render with the reason. The end-to-end test walks the fields and renders a square 720 × 720 through Prepare for drag (2-3 h)
- [x] Orientation in search and on cards: an `orientation:` filter (`portrait`, `landscape`, `square`; `vertical` and `tall` mean portrait) over templates and media alike — a template matches when any of its aspects does, media from its probed size; a Vertical chip beside the media kinds; and a Vertical or Square badge on cards, which for a template of several shapes names the tall ones its landscape poster does not show (1-2 h)
- [x] Vertical safe zones: the stage's safe-area overlay gains the areas a tall frame has to keep clear, described generically rather than named after any one app — a header strip across the top (12%), a controls column down the right (18% wide, mid-frame to the caption), a caption band across the bottom (22%, stopping short of the column) — as fractions of the frame in `src/core/player.ts` beside the broadcast insets. ## 23. Layers in templates (37-56 h)

After milestone 22, which it grows out of, and before milestone 8's schema and authoring guide, for the same reason every format milestone comes first: the guide should describe the format as it ends up.

Milestone 22 gave a template fixed image slots: the author decides where a logo goes and it rides the animation. This milestone lets the **person using the template add a layer the author did not put there** — another line of text, a second logo — and have it ride the animation just the same. A template declares **blocks**, a box per aspect where layers may live; layers stack inside a block and take their part of the template's movement from their position in the stack, so an added line enters, moves and leaves with the design rather than sitting on top of it. The author stays in charge of the look: a layer is drawn with the block's typography and the template's motion unless it is deliberately overridden.

Milestone 22's fixed image slots stay exactly as they are. A slot is the author's; a layer is the user's.

- [x] Template format: `blocks` and `layers`. A block is a box per aspect (fractions of the frame, like an image slot), a stacking direction and spacing, the typography its text layers start from, and whether it is full or may take more. A template's own layers are its defaults, each with a type (`text` or `image`), its properties, and optional `required` so it cannot be removed. The stack position is what the template animates by, so a layer added in the middle takes the movement of the position it is in. Validator with tests, `docs/template-format.md`, an entry in `CHANGELOG.md` (4-6 h)
- [x] Blocks draw. `state.blocks` carries each block for the frame — its box in pixels and the layers that are drawn, in stack order — and the bridge finishes the job: `pulpLayoutBlock` measures, wraps, shrinks or truncates, stacks and places, and `pulpDrawBlock` draws the result, with a per-layer hook called by stack position so an added line takes the movement of the position it is in. The arithmetic is a pure module with unit tests and the bridge mirrors it (4-6 h)
- [x] "Add layer" in the Parameters tab, offering Text or Image, with the block to add it to when a template declares more than one. Reorder within a block, remove (unless the template marks it required), and hide — kept but not drawn, with the stack closing up, so a layer can be taken out of a shot without losing its settings. "Reset layers" restores the template's defaults. The layer list and its edits are a pure core module with unit tests, and every change is undoable with the rest of the parameters. The stacks ride in the same bag of values as the parameters, so undo, a collection card and a render already carry them; a text layer's words are edited here, and the rest of its properties arrive with the item below (5-8 h)
- [x] Text layer properties in the Parameters tab: family, size (as a fraction of the frame, so it holds at every resolution), weight, italic, case, letter spacing, kerning, line height, space before, colour, alignment, and overflow — wrap, shrink to fit, or truncate — folded under each layer's words so the list stays readable, with a one-line summary of how the layer is set. ## 29. Rotate layers on the stage (5-8 h; GitHub issue #31) — done

## 30. Timing: any length, set while editing (18-28 h; GitHub issue #32)

After milestone 29. A template's length is fixed in its manifest today (mostly 5-8 seconds); Set in and Set out only shorten it, the frame rate changes how many frames are drawn but not how long, and only a few templates expose pacing parameters. A lower third that should stay up for twenty seconds cannot. The length becomes something set while editing, and a template says which parts of it may stretch.

- [x] **Templates declare their structure:** an animate-in part, a hold and an animate-out part, in the manifest and validated in the format. The host remaps time so the entrance and the exit keep their designed speed and only the hold stretches or shrinks; a template that declares no structure keeps its fixed length, exactly as now. A pure core module with unit tests, used by the preview and the render alike. *`timing.ts`; `--length` carries it on the command line, and a trim is taken within the chosen length* (4-6 h)
- [x] **Length while editing:** a Length control in the Parameters tab's "Layout and timing" card, in seconds or timecode, with a floor of the entrance plus the exit; the scrub bar shows the in, hold and out parts as shaded segments, and the hold's edges can be dragged. The preview plays at the new length at once, and undo covers every change. *The handle at the graphic's end is the draggable edge: the entrance is fixed at the start, so the hold's own start cannot move. It is a slider, so the arrows work it too* (4-6 h)
- [x] **Everything downstream picks it up:** the Output tab shows the length and trims within it, and presets, collections, CSV batch, the render cache key and a `--length` on the command line carry it. *The length rides with the parameters (`@length`), so presets, collection cards, CSV rows, the undo history and the cache key carry it with no second channel* (3-5 h)
- [x] **Loops and transitions:** backgrounds and animated loops repeat seamlessly to any length (bringing forward milestone 15's loop item); a transition keeps its designed length, with an optional speed control. *A structure is one of three things: a hold that stretches, a `loop` that repeats, or a `scale` that plays the whole graphic faster or slower — which is the transition's speed control, bounded to a quarter and four times its designed speed. 23 loops and 24 transitions declare theirs; which genuinely loop was measured by checking the seam against the motion through the middle, so a fade in and out could not pass for a loop* (3-5 h)
- [x] **Frame sequences play on the stage:** a run of numbered frames previewed on its own shows only its first frame today, because the stage cannot hand a folder of files to a video element. Step it at its rate through the decode path milestone 26 built for Video layers, so previewing a sequence matches how it plays as a layer and in a render; a sequence records no rate, so the one Pulp states becomes a default a person can change. *The stage steps it through the same transport a template uses, asking for one frame at a time by index — no decode path needed on this side, since each frame is already a file. The rate is kept with the item, like a tag* (2-3 h)
- [x] **The bundled templates declare their parts,** titles, lower thirds, callouts and overlays first, and the format guide says how. *85 of 124 declare how they stretch — 23 loops, 24 transitions and 38 with a hold; the other 39 are movement all the way through, countdowns among them, and keep their fixed length. Every hold was measured by rendering the template and differencing each frame of the stretch against its first, at the settings that squeeze it hardest: the "Animate in/out" parameter at the slowest it goes, and a line added to every open block. That measurement replaced an end-to-end check that let a graphic through if it came back to where it started, and all six holds declared before it had motion inside them: four are withdrawn and two corrected. Eleven templates that offered a "Hold, seconds" parameter had it removed, since the length is the control now and the parameter could only shorten a hold inside the template's own duration; three more that offer one keep it, having no hold to declare. Every one draws the same pixels at its own length, so the visual references are untouched* (2-3 h)

## 28. Per-layer timing, transitions and looks (24-36 h; GitHub issue #29)

After milestone 30, whose length a layer's own start and end are set within, and before 27, which has to save all of it. - [x] **A layer's own start and end:** when it appears and when it leaves, in seconds of the graphic's own time, set in the layer's card as seconds or timecode. Seconds, as the Length control is; a timecode field would be the first in the app and belongs with the bars. A span is held to leaving the layer on screen for a moment, since hiding it is a different thing and says so* (4-6 h)
- [x] **The bars under the scrub bar:** one per layer of the block being edited, showing where it is on screen against the graphic's length, with ends that drag and a keyboard equivalent. Milestone 30's in, hold and out parts shade behind them, so a start can be read against what the template is doing. *`stage-bars.ts`: a bar for every layer of every block, under the scrub bar's own scale with the parts directly above, its entrance and exit shaded at the ends; each end is a slider, so the arrows work it, and clicking a bar selects the layer. - [x] **Entrance and exit transitions per layer:** Template, Fade, Slide, Scale, Wipe or None, chosen separately for the entrance and the exit, each with its own duration; Slide and Wipe take a direction. ## 20. Social-ready export (8-13 h)

After milestone 19, which it depends on: a platform preset is mostly an aspect, a resolution and a frame rate, and none of those are choices until templates stop declaring a pixel size.

**The file, not the account.** Pulp makes something the right shape and size for where it is going and then hands it over. No accounts, no logins, no posting through anyone's API: nothing to store a token for, nothing to re-certify, and nothing that breaks when a platform changes its API or its terms.

- [ ] Platform presets: a built-in, versioned list in a pure core module — for each, the aspect, resolution, frame rate, H.264 video with AAC audio, a bitrate target, and the platform's length and file-size limits. Choosing one in the Output tab sets the aspect, resolution, frame rate and encoder together. The list carries the date its limits were checked, and shows it, because this is data that ages; unit tests that every preset's resolution matches its aspect and that the list parses (3-5 h)
- [ ] Length and file-size warnings: before a render, from the trim and the bitrate target; after it, from the file itself. Shown in the Output tab and on the finished job, and never blocking — a limit may have moved since the list was written, and the person rendering may know something it does not (1-2 h)
- [ ] Cover image: a still from a frame picked on the scrub bar, written beside the video at the same aspect and resolution, for the thumbnail or cover a platform asks for separately (2-3 h)
- [ ] Hand-off: "Share…" opens the system share sheet with the rendered file, and "Open upload page" opens the platform's own upload page in the browser with the file revealed in the file manager. An ADR records the choice of hand-off over integration, so the reasoning survives the first request for one-click posting (2-3 h)
