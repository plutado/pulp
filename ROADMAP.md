# Roadmap

Estimates are working hours for one developer, including tests and docs. They are rough; the total range reflects that. Checked items are done. The "still open" row is the sum of the unticked items' own estimates, not the previous figure minus what was finished — recompute it from the items, or it drifts.

"After 1.0" means not needed for the first release, not a place in the queue. Any such item is built whenever adjacent work makes it cheap — while the code it touches is open — and then moves into its milestone's 1.0 part; 1.0 is the line for what a release must have, never a gate on building.

## Where things stand

**Milestone 40, one search wherever you search, is done:** every chooser asks the library through the one `searchMedia`, so the search bar's query language and ranking hold in a picture or clip chooser and in the stage's asset list, and the two choosers are one. **Milestone 39, a right-click menu on the stage, is done before it:** the common layer edits — cut, copy, paste, duplicate, delete, layer order, copy and paste look, reset, start or end at the playhead, edit a line's words, replace a picture or a clip — adding text or an asset where you click, and the stage's own background (now with mid-grey), theater and add-to-collection over bare picture, opened by the pointer or by Shift+F10 and the Menu key, all built from the application menu's own command list and held to it by a test (ADR 0017). **Milestone 38, a bigger stage, is done before it:** the inspector's Parameters, Output and Info are three buttons in the transport row that open a drawer over the results — never over the stage — the right column is gone, so the stage and the results span from the browse panel's edge to the window's right edge, the view controls are a quiet overlay on the stage's corner, and the window fits at every size: the page never scrolls, nothing overlaps, and the picture gets its share, held by a UI test at the default 1280 × 788. Milestone 37, the transport row, is done before it: the player's controls sit in one row across the bottom of the window, above the status bar, the scrub bar and the bars per layer at the window's width, and the stage is only the picture. Milestone 27, projects and the application menu, is done before it: a session saves as a `.pulp` project — guarded, recovered and relinked — and Pulp has its own menu on every platform. Milestone 28 is done before it — a layer has its own start, end, entrance, exit and look, with a bar per layer under the scrub bar — and milestone 30 before that — 85 of the 124 bundled templates declare how they stretch, and the other 39 move all the way through and keep their fixed length — and milestones 26 and 29 before that. Everything before it on the planned order is finished: the renderer and alpha export, the parameter editor, the library with search and categorization, drag-out, packs, the window shell and visual polish, browse and preview, collections, vertical and square formats, the sample library, image slots, layers, the browse panel's find field, and layers moved and resized on the stage. 235 bundled CC0 templates, a 625-file sample-media catalogue, 66 types / 51 themes / 11 styles in the taxonomy, every type at least ten deep, every theme at least six with three assets of its own.

What is left for 1.0: social-ready export (20), 1.0 hardening and docs (8), then packaging — unsigned builds (17) and signing (7). Before those come stock library import (32) and the rest of Lottie animations (35, whose reading, frame-accurate rendering and text-and-colour parameters are in; fonts and images inside, timing from markers, placing on the stage, samples and the limits item remain); a deeper library (36), the transport row (37), the stage's right-click menu (39), the start screen (31), the browse panel that says what things are (34, all but its card sort), layered graphics (33) and converting library media (15) are done. Four verification items wait on hardware: two need the test Mac, and two on Windows are checked in a Windows 11 virtual machine. Known issues and ideas not yet decided are in `docs/ideas.md`.

Milestones keep the number they were given when they were added. Milestones 1 to 23 have GitHub issues of the same number; from 24 on, a new milestone's issue number is given beside its heading, since pull requests share GitHub's numbering. A decision is written here as soon as it is made — a new milestone, or items in an existing one — even when it is low priority and may never be built, so everything decided is visible in one place; `docs/ideas.md` keeps only ideas not yet decided and known issues. The table and the sections below are in **planned order**, which is not numeric order. Packaging and signing (17 and 7) come last, after hardening: packaging is the final step, and what it wraps should be the finished thing. The window layout that the UI milestones build, and why they come in this order, is in `docs/ui-layout.md`.

## 1. Headless frame renderer, production quality (12-20 h)

A first renderer works (offscreen window, PNG frames to ffmpeg). This milestone makes it dependable.

- [x] Automated end-to-end render test that runs when Electron and ffmpeg are available, checking frame count, size and alpha with ffprobe (2-3 h)
- [x] HiDPI: render at device scale 1 explicitly instead of resizing captured frames; verified on a Retina display (2-3 h)
- [x] HiDPI: verify on Windows at 150% scaling. Verified by simulated 150% scaling on Windows CI: the e2e suite renders with Chromium's `--force-device-scale-factor=1.5` (the primary display reports 1.5, as Windows does at 150%) and checks the frames stay pixel-exact; the `windows-latest` job runs the whole suite with `PULP_E2E=1` and passed on ffmpeg 9.0.2 (1 h)
- [x] Large frames: verify 4K and 8K, and portrait sizes for vertical video (1-2 h)
- [x] Throughput: avoid PNG encode/decode by piping raw BGRA (`-f rawvideo -pixel_format bgra`) from `capturePage()`, with `unpremultiply` for alpha templates (ADR 0003 explains why not the `paint` event); benchmarked against the PNG path in `docs/system-design.md` (3-5 h)
- [x] Color: decide and document sRGB/Rec.709 handling: video presets convert with the BT.709 matrix to limited range and tag every frame BT.709 (`scale` + `setparams`), PNG stays sRGB; ADR 0004 (2-3 h)
- [x] Robustness: per-frame timeout for hung templates, delete partial output on cancel or failure, clear errors when a template throws (1-2 h)
- [x] Render queue: several renders in sequence with progress per job (1-2 h)

## 2. Alpha export presets and NLE verification (8-14 h)

- [x] Verify each alpha preset imports with correct transparency in Premiere Pro and DaVinci Resolve on macOS; results in `docs/nle-verification.md`. ProRes 4444 and PNG pass with defaults; QuickTime Animation needs Data Levels: Full in Resolve (now tagged full-range RGB, re-check); HEVC: no alpha in Premiere, Alpha Mode: Straight in Resolve; WebM: not importable in Premiere, broken alpha in Resolve (3-5 h)
- [ ] On the test Mac: re-check whether Resolve's Data Levels Auto honors the new full-range QuickTime Animation tag (1-2 h)
- [ ] Verify alpha import in Premiere Pro and Resolve on Windows, in a Windows 11 virtual machine on the maintainer's Mac (also used for debugging Windows-only failures); if either app can't run in the VM, the check waits for a real Windows machine and stops blocking 1.0 (1 h)
- [x] Straight versus premultiplied alpha: Chromium captures premultiplied (measured by a probe), every preset is written straight, Premiere and Resolve read ProRes, PNG and Animation as straight; no export option, HEVC's Resolve default documented as a caveat; ADR 0008 (2-3 h)
- [x] Additional presets: QuickTime Animation (qtrle) for older workflows, HEVC with alpha on macOS via VideoToolbox where available; shown as unavailable elsewhere with the reason; ADR 0005 (2-3 h)
- [x] Preset options: frame-rate override from the standard list, background color picker for flattening, in/out points as timecode or frames; in the inspector and as `--fps`, `--background`, `--in-point`, `--out-point`; verified on macOS and Windows CI (1-3 h)

- [x] Browse tree in the browse panel (`src/core/browse-tree.ts`, pure and tested), replacing milestone 11's flat node list: Quick access (Favorites, Recently used), Types (group → type, with an Untyped node for templates of category "other" and media no folder typed), Themes (built-in groups plus a Custom group), Styles and Folders ("Built-in templates" first), each node with a count. ## 19. Vertical and square formats (13-21 h)

Before milestone 8, which writes the authoring guide and the JSON Schema: both should describe the format as it ends up, not one that is about to change underneath them.

**A template is defined by its aspect ratio, not by a pixel size.** A lower third is a lower third at 1920 × 1080 and at 1080 × 1920; what differs is the shape of the canvas and where things sit in it. Today's manifest declares `width` and `height`, which pins every template to one resolution and makes a vertical version a second template to write and maintain. This milestone moves the pixel size to render time and leaves the template saying only which shapes it is drawn for.

- [x] Template format: a template declares the aspect ratios it supports (`aspects`: 16:9, 9:16, 1:1, 4:5) instead of a pixel size, and draws relative to the canvas it is handed; the frame state's `width` and `height` are now the render's, passed in by the caller rather than read off the manifest. The output resolution is chosen at render time through a pure `src/core/aspect.ts` (standard sizes per aspect, 720p to 4K and 8K for 16:9; an exact size; the checks that a size is of its aspect), carried in the render options as `aspect`, `width` and `height` and as the headless `--aspect` and `--size` flags. Manifests with `width` and `height` keep working: the aspect is inferred (a built-in one within 1%, else the reduced ratio such as 4:3, at which the template renders at that one size) and the size becomes the default resolution. The renderer sizes its offscreen window from the plan's size rather than the manifest, the capture-size check and ffmpeg's input follow it, and thumbnails, hover-scrub strips and the preview take the template's default size. The library re-reads templates once (schema 5) so stored manifests carry their aspects. Validator with tests, `docs/template-format.md`, ADR 0012; the render test proves a shape-only fixture at its default, tall with `--aspect`, square with `--size`, and the refusals (4-6 h)
- [x] Output tab: an aspect choice for templates that support more than one (hidden otherwise), and a resolution for every template — the template's own size or the aspect's default first, the standard list for that aspect, then a custom width and height checked against the aspect — carried in the render options, written to the collection card being edited, and read back from one. The preview follows the choice through a shared `frameSize` signal: the box takes the shape and the template is drawn for that canvas. The options note names the size when it is not the template's own, and a size that is not of the aspect blocks Render with the reason. The end-to-end test walks the fields and renders a square 720 × 720 through Prepare for drag (2-3 h)
- [x] Orientation in search and on cards: an `orientation:` filter (`portrait`, `landscape`, `square`; `vertical` and `tall` mean portrait) over templates and media alike — a template matches when any of its aspects does, media from its probed size; a Vertical chip beside the media kinds; and a Vertical or Square badge on cards, which for a template of several shapes names the tall ones its landscape poster does not show (1-2 h)
- [x] Vertical safe zones: the stage's safe-area overlay gains the areas a tall frame has to keep clear, described generically rather than named after any one app — a header strip across the top (12%), a controls column down the right (18% wide, mid-frame to the caption), a caption band across the bottom (22%, stopping short of the column) — as fractions of the frame in `src/core/player.ts` beside the broadcast insets. Shown from the same toggle and only while the previewed shape is portrait, for templates at a tall aspect and for tall media alike; the unit test checks the zones stay inside the frame and apart, the end-to-end test turns them on at 9:16 and watches them go at 16:9 (1-2 h)

The windowing math wants one row pitch, so a grid takes its row height from the tallest picture in it (`tallestRatio`, `cardHeight(width, ratio)` in `src/core/results-view.ts`) and the container publishes that pitch and the picture height as custom properties; an all-wide grid is exactly what it was. ## 23. Layers in templates (37-56 h)

After milestone 22, which it grows out of, and before milestone 8's schema and authoring guide, for the same reason every format milestone comes first: the guide should describe the format as it ends up.

Milestone 22 gave a template fixed image slots: the author decides where a logo goes and it rides the animation. This milestone lets the **person using the template add a layer the author did not put there** — another line of text, a second logo — and have it ride the animation just the same. A template declares **blocks**, a box per aspect where layers may live; layers stack inside a block and take their part of the template's movement from their position in the stack, so an added line enters, moves and leaves with the design rather than sitting on top of it. The author stays in charge of the look: a layer is drawn with the block's typography and the template's motion unless it is deliberately overridden.

Milestone 22's fixed image slots stay exactly as they are. A slot is the author's; a layer is the user's.

- [x] Template format: `blocks` and `layers`. A block is a box per aspect (fractions of the frame, like an image slot), a stacking direction and spacing, the typography its text layers start from, and whether it is full or may take more. A template's own layers are its defaults, each with a type (`text` or `image`), its properties, and optional `required` so it cannot be removed. The stack position is what the template animates by, so a layer added in the middle takes the movement of the position it is in. Validator with tests, `docs/template-format.md`, an entry in `CHANGELOG.md` (4-6 h)
- [x] Blocks draw. `state.blocks` carries each block for the frame — its box in pixels and the layers that are drawn, in stack order — and the bridge finishes the job: `pulpLayoutBlock` measures, wraps, shrinks or truncates, stacks and places, and `pulpDrawBlock` draws the result, with a per-layer hook called by stack position so an added line takes the movement of the position it is in. The arithmetic is a pure module with unit tests and the bridge mirrors it (4-6 h)
- [x] "Add layer" in the Parameters tab, offering Text or Image, with the block to add it to when a template declares more than one. Reorder within a block, remove (unless the template marks it required), and hide — kept but not drawn, with the stack closing up, so a layer can be taken out of a shot without losing its settings. "Reset layers" restores the template's defaults. The layer list and its edits are a pure core module with unit tests, and every change is undoable with the rest of the parameters. The stacks ride in the same bag of values as the parameters, so undo, a collection card and a render already carry them; a text layer's words are edited here, and the rest of its properties arrive with the item below (5-8 h)
- [x] Text layer properties in the Parameters tab: family, size (as a fraction of the frame, so it holds at every resolution), weight, italic, case, letter spacing, kerning, line height, space before, colour, alignment, and overflow — wrap, shrink to fit, or truncate — folded under each layer's words so the list stays readable, with a one-line summary of how the layer is set. The host already resolved all of them (the item above); this is the editing surface, and with it the Title Card's font and text colour are back, as layer properties (4-6 h)
- [x] Image layers, SVG or PNG: milestone 22's picker, its by-id grant and its treatments (original, tinted, white, black, shadow or glow), plus size and alignment. No font properties; a layer is one kind of thing or the other. An image layer stacks with the lines and takes the movement of its position, and hides, moves, removes and resets like them; proved on Title Card and Lower Third Bar, a mark added above the title riding the first position's fade, at 16:9 and 9:16 (3-4 h)
- [x] Fonts: a bundled set of open-licence families — Inter, Montserrat, Oswald, Bebas Neue, Source Serif 4, Playfair (where Playfair Display now lives: its upstream became the Playfair superfamily, whose display cut is the large end of its optical-size axis), JetBrains Mono, Caveat, Dancing Script, Noto Sans — each one's licence confirmed from the upstream licence file rather than from a package listing, the two with a Reserved Font Name shipped unmodified and hash-checked, with `docs/font-credits.md` naming the family, the version, the licence and where it came from, and ADR 0014 on the set, the licences and the delivery under each page's own origin. - [x] Layers travel: saved presets, collection items, `.pulpcollection` files, `--param` headlessly, and a CSV batch with a column per layer. The render cache key covers the layers, so an added line renders afresh, and undo covers adding, removing, hiding, reordering and every property. They ride in the same bag of raw values as the parameters, so every route that carried parameters carries them; `--param '@layers={…}'` takes JSON, patching the template's stack and naming a bad block, a bad layer or bad JSON rather than falling back; each route has its own check (3-5 h)

## 35. Lottie animations (17-29 h, plus 3-5 h after 1.0; GitHub issue #37)

After milestone 33. Lottie is the animated vector format After Effects exports through Bodymovin and many apps and sites use: a JSON file (or a zipped `.lottie`) that describes shapes, text, images and their keyframes. It is motion graphics already made, so Pulp reads it as an item that plays, renders and is edited like a template, rather than as a picture.

**How a person uses it (decided 2026-10-30).** Nobody should need to know the word "Lottie": to the person using Pulp it is one more graphic that moves, in the same categories as templates, previewed and scrubbed the same way, its text and colours in the Parameters drawer, rendered with alpha and dragged into an editor; "Lottie" is a small badge and a line in the Info tab, as "Alpha" is today. Its place is the small animated elements templates are weak at — animated icons, arrows, checkmarks, likes and subscribe bells, emoji and stickers, confetti and sparkles, underlines and scribbles — and its main use is as a layer dropped onto a lower third, a title or an end card. A person meets it in the browse panel (a starter set made for Pulp), from their own files (a Bodymovin export dropped into a library folder) or from stock downloads (a `.lottie`'s author and licence shown in the Info tab; Pulp never uploads or redistributes anything). It works when someone can find an animated arrow, recolour it, drop it onto a lower third, time it to land with the title and render the result with alpha in about a minute, without reading anything about Lottie.

- [x] **Read and index:** `.json` Lottie files (told apart from other JSON by their shape) and `.lottie` archives, with their size, frame rate, length and markers; a poster and hover-scrub strip like any template, typed and filed by the taxonomy like other items. *A Lottie is a template read from one file (`src/core/lottie.ts`, `loadLottie`): a `.json` is sniffed by its first four kilobytes for Bodymovin's header keys so no settings file is parsed whole, a `.lottie` is read for its first animation, its images and its author, the manifest is made from the file — its own size as the default resolution, every built-in aspect declared, its rate and length, transparent — and the entry carries the file, the markers and what the player cannot draw. Its type and themes come from its folders as a clip's do; the key is the file's path and the stat signature its own, so the posters, strips, the stage, the Info tab (source, markers, what is editable, what is not drawn) and renders see it as any template* (2-4 h)
- [x] **Render frame-accurately** through the existing renderer with an open-source player (lottie-web, MIT) stepped to each frame rather than played in real time, at any output size and aspect (fitted, filled or centred), with alpha export as for templates. *The template protocol answers a Lottie's entry with a generated page (`src/core/lottie-page.ts`) that loads lottie-web 5.13's light build — the SVG renderer without expressions and effects, the build that runs without `eval` under the template CSP — from a reserved path, and steps it with `goToAndStop(time × fr)` per frame; another output rate lands between keyframes and the player interpolates. A Fit parameter sits the animation in a frame of another shape: fitted, filled, or at its own size centred. The end-to-end test reads a keyframed square's pixels back on frames 0 and 5, checks the alpha range, and renders a `.lottie` fitted into a square. Packaging (17) must carry `lottie-web/build/player/lottie_light.min.js`* (3-5 h)
- [x] **Edit what the file exposes:** text layers, colours and images become parameters in the Parameters tab — Lottie's slots and theming where the file has them, otherwise its named text layers and fill colours — saved with the item like any other parameters. *Slots first (a colour or a text slot each becomes a parameter, and what is bound to one is reached through it alone), then every static text layer (a Text field under the layer's name) and every distinct static colour once — fills, strokes, solids and text colours, labelled by the nearest named shape, group or layer, with "also used in N places" where a palette colour is shared — under a Colours card; a value is written into a copy of the animation's JSON at load, so the player reads it as the file's own. Text that changes over time, animated colours and gradients are left as they are, the first named on the item; dotLottie themes are named as not read. Images are not parameters yet: an image layer draws the picture the file names, which comes with the fonts-and-images item* (4-6 h)

## 20. Social-ready export (9-14 h)
